# Game plugin

`plugin/` builds `thuum.dll`, the SKSE plugin a mod manager installs beside `thuum.esp`. The DLL contains the shout table, the pinned hold classifier and a CPU inference runtime. Nothing is downloaded, started or configured at run time. The design record is [design.md](design.md); how the classifier is trained is in [training.md](training.md).

## What it does

With the lesser power Thuum equipped, the player holds the Shout button and speaks the dragon words. On release the plugin classifies the held audio and fires the spoken shout at the spoken word count through the game's own shout path, with its normal animation, sound, effects and recovery time. With anything else equipped, the Shout button behaves as in the vanilla game.

## Decisions

- **Runtime: [tract](https://github.com/sonos/tract) 0.22.4, statically linked.** It runs the classifier from a memory buffer with no ONNX Runtime library and cross-compiles from Linux to `x86_64-pc-windows-gnu`. On the eSpeak NG synthesized "fus" and "fus ro dah" clips in `plugin/tests` its 81 entry scores match ONNX Runtime's to within 1e-3 and both decide the spoken entry; the CTC decision matches the Python implementation to 1e-4. `python3 -m tools.classifier_fixture <classifier.onnx>`, run from the repository root, synthesizes both clips again and rewrites them and `plugin/tests/classifier-fixture.json` with ONNX Runtime's scores and the Python decision (it needs `espeak-ng`, `sox`, `numpy` and `onnxruntime`); the Rust and Python suites both check against the fixture.
- **Toolchain:** Rust (pinned in `plugin/rust-toolchain.toml`) and the nixpkgs MinGW-w64 cross compiler (`plugin/shell.nix`), with the C runtime and winpthreads linked statically. The DLL imports only Windows system libraries: kernel32, ntdll, ole32, oleaut32, combase, propsys, rpcrt4, shell32, advapi32, bcrypt, bcryptprimitives, userenv, ws2_32, msvcrt and two api-ms-win-core sets. There is no C++ runtime and no ONNX Runtime.
- **Hold classifier:** `data/hold-classifier.json` pins the ONNX file (SHA-256 and size, checked by `build.rs`), its input, output and per-word bonus, and the build embeds the file. The classifier takes the whole hold as 16 kHz PCM, peak-normalised to 0.5, and returns frame log-probabilities over a CTC blank and the 81 dragon words. Each entry's score is the CTC log-likelihood of its words plus the bonus per word, as in `thuum.hold_classifier`; the argmax fires, the first entry on a tie. A hold shorter than the pinned `min_samples` (8000) is padded with silence to it.
- **Trigger, hold to shout:** thuum replaces entry 6 of the player `ShoutHandler` vtable, its button handler. The vtable was found through the executable's RTTI type descriptor `.?AUShoutHandler@@`; among the player input handlers the button handler is entry 6 (the shout, sneak, ready-weapon, auto-move and attack/block handlers override it, the look handler keeps the base no-op). The vanilla handler reads the button event's value and held seconds, and the hook reads the same fields. Before patching, the plugin checks that the slot still holds the vanilla handler; if not, it logs that and disables itself.
- **Voice power:** voice control is the lesser power Thuum. `thuum.esp`, ESL-flagged with `Skyrim.esm` as its only master, defines it with three records: the power (`0x801`), a hidden script-archetype effect with no script (`0x800`) and a start-game-enabled quest (`0x802`) whose Player alias holds the power as an alias spell, which gives it to the player in a new game or an existing save. A lesser power rather than a shout record, because the voice path already restores a power as the previous selection, and a shout record would need its own word records the player would have to unlock before equipping it. Its fields follow the vanilla lesser powers (Voice equip slot, fire-and-forget on self). `plugin/src/esp.rs` writes the file byte for byte (`cargo run --bin thuum-esp -- <path>`) and `plugin/tests/esp.rs` checks its records. At data load the plugin finds the file among the loaded plugins through the game's data handler, computes the power's runtime form ID from the file's light or full index and checks it is a spell. If the file is not loaded, the plugin logs that and disables itself before opening the microphone, and the game is vanilla.
- **Who owns a hold:** a press belongs to thuum when Thuum is the player's equipped power, or when a voice shout that replaced Thuum is still in flight. An owned hold, press through release, never reaches the vanilla handler. Every owned hold listens; nothing about the audio decides whether it does. Any other press goes to the vanilla handler unchanged, as it does when the plugin is disabled. If the plugin disables itself mid-hold, the rest of that hold goes to the vanilla handler, which can only cast Thuum's empty effect. A press that arrives while a hold is still believed down (its release was lost, for example inside a menu that blocks the Shout handler) cancels the old hold first. Focus loss delivers a release, so it splits a hold and each part is decided on its own audio. Loading or starting a game cancels a listening hold without a decision.
- **Hold decision:** the recognizer thread cuts capture into 80 ms chunks and keeps the last 4 (320 ms) as pre-roll, so a first syllable spoken with the press is kept. A hold longer than 4 s, pre-roll and tail included, keeps its last 4 s. After the release it waits two more chunks, so the last word is in the window, or 250 ms if audio stops; a new press before then decides the previous hold at once. It then classifies the audio and fires the nearest of the 81 shout-and-word-count entries, with no rejection threshold and no speech gate. With no capture stream delivering audio, a hold cannot close until audio returns, and its decision is then refused as late. Press and release cross threads as one atomic hold state (hold number and held bit); the recognizer recovers their order when several edges fall between two audio packets. Classification runs on the recognizer thread, so the capture buffer holds 1 s to cover it.
- **Firing path:** the plugin calls the engine functions the game's leftover Kinect voice-command code calls: it records the shout and the player's previous selection in the speech-recognition object, calls `ActorEquipManager::EquipShout`, then `Actor::StartShout(player, shout, tier - 1)`. The player's voice update fires that tier with the normal cast check and recovery time, and the game re-equips the previous selection afterwards (an empty slot, a shout or a power). When the engine accepts a start but the shout never runs, or `StartShout` refuses, the game does not restore the selection; the plugin then re-equips Thuum through the engine's `EquipSpell` into the vanilla VoiceEquip slot. Each settled shout logs whether the game set a recovery time, whether the selection was restored and whether the plugin re-equipped it.
- **Refusals:** a command is refused, never downgraded or deferred, when the player is not in the world (main menu, loading), a menu pauses the game, the controls the Kinect code requires are disabled (control-map flags 0x40 and 0x800), the player is in beast form, the voice is busy or recovering, a requested word is not unlocked, or more than 500 ms have passed since the release. The 500 ms covers recognition, the queue and the wait for the input poll, so a late decision is refused rather than firing a shout the player no longer expects. Each firing logs `latency_ms` from release. Loading or starting a game drops queued commands.
- **Game-thread context:** commands from the recognizer thread wait in a bounded queue (4). A sink registered on the game's input-event dispatcher drains it during each frame's input poll, the context in which the game's own shout key handler starts shouts. SKSE's task queue is not used: during play it runs on a job thread that can overlap input processing.
- **Spoken words in the Magic menu:** once the shout handler is hooked, the plugin rewrites each table shout's word translations to lead with the word as spoken in `data/shouts.json`, so "Force" becomes "Fus (Force)" and the shout card names what to say for each learned word. A translation that already leads with the spoken word is left alone. It is a runtime change rather than a record override, so it keeps whatever translation the load order settled on. The new strings come from the engine's own string constructor; the translation offset (`+0x30`) and word form type (`0x76`) were read from each runtime's word loader.
- **Capture:** shared-mode WASAPI on the default capture endpoint, on the recognizer's own thread, resampled to 16 kHz mono. A stream that delivers nothing for 2 s, fails, or whose default endpoint changes is reopened; a failed open is retried every 500 ms. Under Proton the default endpoint is Wine's single PulseAudio input, whose ID never changes: the audio server moves the untargeted stream when its default source changes, and a source with no available port never becomes the default, so capture waits until a source that can deliver audio exists. On native Windows the endpoint ID changes and the plugin reopens.
- **Robustness:** a classifier error drops that hold without a decision and is logged. Every entry point from the game catches panics; after one, or if the input sink cannot be registered, the plugin logs it, stops acting and stops the recognizer. Logging runs on its own thread, so the game thread never waits on disk.
- **Log:** `My Games/Skyrim Special Edition/SKSE/thuum.log` or `My Games/Skyrim VR/SKSE/thuum.log`, beside SKSE's logs. Each launch appends a `session start unix=<seconds>` line; a log above 4 MiB at launch is renamed to `thuum.1.log`, bounding the two files to about 8 MiB. Each decided hold logs the nearest entry and its score, the runner-up and its score, their margin, the hold window in ms, the loudest chunk's RMS outside the pre-roll, and the classification time. No audio is written.
- **Game forms:** `data/game-forms.json` names each shout's form by plugin file and local form ID. At data load the plugin takes each file's index from the loaded-file list, so a load order that moves Dawnguard or Dragonborn off the vanilla indices still resolves the DLC shouts. `python3 -m thuum game-forms <game Data dir>` checks that every entry is a three-word shout in that game's master files.

## Skyrim SE and VR

One DLL serves Skyrim Special Edition 1.7.104 and Skyrim VR 1.4.15. Each runtime has a table of engine addresses and the struct offsets that differ (`plugin/src/game.rs`), found by static analysis of that executable. The plugin picks the table whose PE link timestamp matches the running executable and refuses any other. SKSE for Special Edition reads the `SKSEPlugin_Version` export; SKSE VR calls `SKSEPlugin_Query`, which accepts only those two executables. No Address Library is used.

Address handling for VR:

- The VR addresses were found by static analysis. Each was matched to its Special Edition counterpart by code, not by name.
- The Kinect shout command handler is the Special Edition one instruction for instruction, and its operands give form lookup, the control map, the menu controls (beast form), the player, the voice state, `EquipShout` and `StartShout`. The speech-recognition object is the global its constructor sets. Voice recovery and `EquipSpell` have the Special Edition bodies. The input dispatcher and its sink registration are the ones the player-controls constructor uses.
- The actor's process and selected power sit 8 bytes lower than in 1.7.104, and VR's button event carries 8 more bytes, so value and held seconds are at `+0x30` and `+0x34` instead of `+0x28` and `+0x2C`. The `ShoutHandler` vtable was found through RTTI as in Special Edition; its button handler is also entry 6.
- The VR data handler keeps loaded plugins in an inline array of 255 and has no light-plugin list, so `thuum.esp` takes a full index there despite its ESL flag. Skyrim VR ESL Support (`skyrimvresl.dll`) moves light plugins into its own file collection, laid out like Special Edition's and returned by its `GetCompiledFileCollectionExtern` export; when that export exists the plugin reads that collection instead, and `thuum.esp` gets a light form ID (`FE` and its index).
- The string constructor used for the Magic menu translations was matched by code and by the case-folding hash table both runtimes use.

## Build and test

`python3 -m thuum package <dir>` builds the shipped DLL and `thuum.esp` and writes the mod-manager archive; see [package.md](package.md). A mod-manager install puts `thuum.esp` in `Data` and `thuum.dll` in `Data/SKSE/Plugins`, and the plugin file is enabled in the load order. SKSE (Special Edition) or SKSE VR is a prerequisite.

The build embeds the pinned classifier, so tests need it too. `THUUM_CLASSIFIER` names the file and `build.rs` checks its size and hash. The download URL is in `data/hold-classifier.json`:

```sh
mkdir -p .scratch
curl -L --fail -o .scratch/hold-classifier-accent-r3.onnx \
  "$(python3 -c 'import json; print(json.load(open("data/hold-classifier.json"))["url"])')"
cd plugin
THUUM_CLASSIFIER=../.scratch/hold-classifier-accent-r3.onnx nix-shell shell.nix --run 'cargo test'
```

Windows builds, run inside the same shell:

```sh
cargo build --release --target x86_64-pc-windows-gnu
cargo build --release --target x86_64-pc-windows-gnu --features probe
cargo build --release --target x86_64-pc-windows-gnu --features test-hook
```

The shipped DLL exports only the SKSE entry points. `--features probe` adds the `thuum_probe` export and the `thuum-probe.exe` harness. `--features test-hook` makes the plugin, when `THUUM_TEST_DIR` names a directory, read each `*.cmd` file there containing `<shout> <tier>` (for example `unrelenting_force 3`) and submit it as the same command a decided hold produces; such commands go through the same refusals, with the 500 ms limit counted from when the file was read. A compiler-cache `RUSTC_WRAPPER` breaks the `cc` crate's cross C build, so clear it for Windows builds.

## Probing under Proton and Windows

`thuum-probe.exe <seconds> [nohold]` loads `thuum.dll` from its own directory, runs the recognizer on the default capture endpoint for that many seconds, pressing the hold signal at the start of each second and releasing it at the end as the hooked Shout button would (`nohold` never presses), then benchmarks classification of 1 to 4 s holds. It prints one JSON report: per-second capture counters (opens, samples, errors, stalls, last error, peak RMS), each second's hold decisions with release-to-decision time, and the classification timings. Copy `thuum.dll` and `thuum-probe.exe` from a `--features probe` build into one directory and pass that as the build directory below.

- `plugin/proton-probe.sh <proton wine64> <build dir> <out dir>` runs the probe for 30 s under Proton's Wine in a fresh prefix with a private PulseAudio server holding two null sinks, A and B. It speaks synthesized dragon words (`espeak-ng`) into A, switches the default source to B, removes A, speaks into B, kills and restarts the server, and speaks again, logging each step to `events.log`. Outside the Steam runtime Proton's Wine needs the host `libpulse`, which the script puts on `LD_LIBRARY_PATH`. It needs `pulseaudio`, `espeak-ng` and Wine's `wineserver` beside the given `wine64`.
- `plugin/nohold-probe.sh <proton wine64> <build dir> <out dir> <mix.wav>` runs the probe in `nohold` mode while playing a long mix (for example an hour of game dialogue, music and effects) into the private server's microphone, then requires no decision, no owned hold, no stall and at least 2,400 audible seconds. A decision only starts at a press of the hooked Shout input, so zero is what the design guarantees; the run guards against any other path from audio to firing. It needs `pulseaudio`, `sox` and `python3` (for example `nix-shell -p pulseaudio sox python3`).
- `plugin/windows-probe.sh <ssh guest> <build dir> <out dir> [reconnect|nomic]` runs the probe on a Windows machine reached by ssh, with PowerShell as the ssh user's shell, that user an administrator logged on at the console, and microphone access for desktop apps on. The guest needs two capture endpoints, named Microphone and Line In, fed from two host PulseAudio sinks named `micA` and `micB`; `PULSE_SERVER` names the host server. The script copies the build and `windows-audio.ps1` to `C:\thuum`, checks the hashes there, starts the probe as a scheduled task in the console session (where a game runs), and plays speech while disabling, re-enabling and switching endpoints and restarting the Windows Audio service (`reconnect`), or starts with both endpoints disabled and enables them one by one (`nomic`). On exit it stops the probe, re-enables both endpoints and makes Microphone the default again.
- `plugin/windows-probe-check.py <reconnect|nomic|nohold> <probe.json>` checks a report: speech bursts and capture opens expected for the mode, no recognizer errors, and one decision for every owned hold that capture fed. The shell scripts run it at the end.
- `plugin/windows-audio.ps1 list|default <name>|visible <name> <0|1>` lists capture endpoints and, through the undocumented `IPolicyConfig` interface, sets the default or disables and re-enables an endpoint.
- `plugin/windows-load.ps1 <dll>` loads a DLL with `LoadLibraryW`, resolves the SKSE exports and `thuum_probe`, and lists the modules the load pulled in.

## Measured behaviour

- Classification of a 1/2/3/4 s hold takes about 50/70–100/100–150/180–230 ms on an x86-64 CPU, under Proton and on native Windows alike.
- In game, release to firing over 100 consecutive holds of speech played into the microphone had a median of 267 ms, p95 334 ms and maximum 350 ms; none reached the 500 ms limit.
- During play the recognizer thread used about 4% of one core; listening with no hold, under 2%.
- Capture follows the default source under Proton through a source switch, a source removal and an audio-server restart, and reopens on native Windows when the default endpoint is disabled, changed or re-enabled, after a Windows Audio restart, and when the first endpoint appears after starting with none.
- An hour of game dialogue, music and effects played into the microphone with no press made no decision.
